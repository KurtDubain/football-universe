## 2. 当前实现基线与问题

### 2.1 已有能力

- `CoachStyle` 已有进攻、防守、均衡、控球和反击五种风格。
- `CoachBase` 已有 `rating`、攻防增益、赛事适性、抗压、风险倾向和稳定性等属性。
- 赛前预测和正式比赛已经复用 `calculateMatchModel`，具备统一解释来源的基础。
- 比赛已有主客场、中立场、世界杯东道主、杯赛、两回合、伤停、换人和红牌语义。
- 直播已有真实首发快照、事件序列、定位球、点球大战和确定性演出种子。

### 2.2 需要解决的问题

- 首发人数固定为 `1 GK + 4 DF + 3 MF + 3 FW`，所有球队事实上都是 4-3-3。
- Canvas 使用单一 `BASE_FORMATION`，不同教练和球队在直播中的基础结构相同。
- 教练主要通过攻防数值进入比赛模型，风格、风险倾向和评分缺少完整可见反馈。
- 当前实力差超过阈值时，弱队直接获得进攻和中场补偿；它能增加悬念，却不能表达低位防守、收缩空间或反击策略。
- `MatchFixture` / `MatchResult` 暂无冻结的双方战术快照，赛后解释和回放无法追溯本场部署。
- 教练详情、球队详情和比赛报告没有共同回答“这位教练想怎么踢、今天为什么这样踢、产生了什么倾向”。

## 3. 系统边界与权威来源

### 3.1 单一权威链路

后续实现必须遵循以下方向：

```text
教练长期身份 + 可用阵容 + 比赛上下文 + 独立确定性扰动
                         ↓
                  本场战术快照
                         ↓
       首发选择 / 比赛模型 / 事件倾向 / 战术解释
                         ↓
         赛前 UI / 战报 / 新闻 / 直播站位与播报
```

- 预测和正式模拟必须调用同一个纯函数生成战术，不能在 UI 内另算一套阵型或策略。
- 战术决策使用由宇宙种子、赛季、fixture ID 和教练 ID 派生的独立随机源，不能扰动现有比赛 RNG 调用顺序。
- 完赛后冻结最小战术事实；展示文案从枚举和原因代码派生，不在存档中复制长文本。
- 直播只消费权威快照，不能根据比分或画面自行发明与赛果不一致的部署。
- 自动推进、批量推进、关键节点推进和未来可能的自动模式必须走同一入口。

### 3.2 第一版不做

- 不提供玩家手动选择阵型或策略。
- 不增加边锋、前腰、后腰、翼卫、伪九号等细分球员位置。
- 不增加三中卫体系、非对称阵型或十余种阵型。
- 不实现完整的比赛中途换阵型、手动换人和逐分钟战术指令。
- 不让阵型、策略、原有教练 buff 和弱队补偿重复叠加。
- 不增加战术训练、熟练度、复杂化学反应或新的经营资源。
- 不根据一次胜负武断显示“战术成功/失败”；赛后只能展示模型中真实存在的倾向和可核验比赛数据。

## 4. 数据模型草案

最终字段名可在实现审计后微调，但语义必须保持单一。

```ts
export type Formation = '4-3-3' | '4-2-3-1' | '4-4-2' | '5-4-1';

export type MatchApproach =
  | 'pressing'
  | 'control'
  | 'balanced'
  | 'counter'
  | 'low_block';

export interface MatchTacticsSnapshot {
  coachId?: string;
  formation: Formation;
  approach: MatchApproach;
  reasonCodes: TacticalReasonCode[];
  matchupTags: TacticalMatchupTag[];
  executionBand: 'limited' | 'steady' | 'elite';
  impact: {
    attack: number;
    midfield: number;
    defense: number;
    possession: number;
    chanceQuality: number;
    variance: number;
  };
}
```

建议的数据落点：

- `CoachBase.preferredFormation?: Formation`：教练长期身份。创建世界后应始终补齐；可选声明只用于加载旧数据或中间迁移。
- `MatchResult.homeTactics?` / `awayTactics?`：冻结完赛事实，支持战报、回放和历史解释。
- 若赛前 fixture 必须跨刷新保留已经公开的部署，再评估是否给当前窗口 fixture 写入精简预案；不要默认复制到所有未来赛程。
- 不给 `TeamBase` 增加独立永久阵型。球队当前战术由当前教练决定，教练空缺时使用明确的临时默认方案。
- 不持久化“常用阵型次数”“战术胜率”等可由有限赛果派生的数据。

兼容回退：

- 缺少 `preferredFormation` 的既有教练，按 `style + coachId` 确定性补齐，不因每次加载而改变。
- 缺少战术快照的旧比赛回放使用 `4-3-3 + balanced`，并标记为“历史比赛未记录部署”，不伪造教练影响。
- 教练空缺时使用 `4-3-3 + balanced` 的临时方案，不获得教练执行加成。

## 5. 教练长期身份

### 5.1 首选阵型分布

首选阵型在教练生成时固定，教练换队后继续携带，形成可追溯的执教身份。以下是建议初始权重，最终需要分布审计校准：

| 教练风格 | 4-3-3 | 4-2-3-1 | 4-4-2 | 5-4-1 |
|---|---:|---:|---:|---:|
| 进攻 | 55% | 30% | 15% | 0% |
| 防守 | 0% | 30% | 15% | 55% |
| 均衡 | 15% | 40% | 35% | 10% |
| 控球 | 55% | 40% | 5% | 0% |
| 反击 | 5% | 35% | 35% | 25% |

- 默认教练和新生成教练使用同一套权威生成函数。
- 退役球员转型教练时，继续先推导风格，再由风格和稳定 UUID 产生阵型。
- 教练不会每场随机换阵型。只有严重位置缺员导致首选阵型无法组成时，才选择同风格兼容的备用形状。
- 第一版不单独保存“第二阵型”或“战术适应性”字段。

### 5.2 现有教练属性的新职责

- `style`：决定策略基础权重和可见的足球理念。
- `preferredFormation`：决定常规首发结构和直播基础站位。
- `rating`：决定计划执行稳定度，建议只在约 `0.85～1.05` 的系数范围内修正战术效果。
- `riskBias`：影响主动压迫、反击和低位防守的选择概率，不直接重复增加进球。
- `pressureResistance`：在决赛、淘汰赛、德比和保级关键战中减少策略失真或过度保守。
- `leagueBuff` / `cupBuff`：继续表达赛事适性，但要并入统一教练效果预算，不能在战术效果之外无上限叠加。
- `attackBuff` / `defenseBuff`：保留教练能力差异，但需要重新校准为统一预算的一部分。
- `stabilityBuff` / `moraleBuff`：继续作用于球队长期状态，不冒充阵型克制。

## 6. 四种阵型

| 阵型 | 首发结构 | 主要特征 | 明确代价 |
|---|---|---|---|
| 4-3-3 | 1 GK / 4 DF / 3 MF / 3 FW | 边路宽度、前场接应、主动压迫 | 高位投入后身后空间较大 |
| 4-2-3-1 | 1 GK / 4 DF / 5 MF / 1 FW | 中路控制、双层保护、攻守平衡 | 禁区内持续人数和直接冲击略少 |
| 4-4-2 | 1 GK / 4 DF / 4 MF / 2 FW | 双前锋、直接推进、转换接应 | 中场中央可能被人数压制 |
| 5-4-1 | 1 GK / 5 DF / 4 MF / 1 FW | 禁区保护、压缩空间、守住领先 | 控球、主动进攻和持续压迫明显下降 |

初始数值只作为校准方向，不直接视为最终参数：

- 4-3-3：进攻约 `+2%`、中场约 `+1%`、防守约 `-2%`，提高宽度与高位丢球后的转换风险。
- 4-2-3-1：中场约 `+2%`、防守约 `+1%`，进攻接近中性，降低比赛波动。
- 4-4-2：进攻约 `+1%`、中场约 `-2%`，提高直接推进和双前锋参与度。
- 5-4-1：进攻约 `-5%`、中场约 `-1%`、防守约 `+4%`，明显降低控球倾向。
- 应在应用阵型后归一化整体能力预算，避免某个阵型获得无代价的总强度优势。

## 7. 五种单场策略

| 策略 | 比赛倾向 | 代价 |
|---|---|---|
| 主动压迫 | 更积极争夺球权、提高射门与前场事件密度 | 防线身后空间、比赛波动增加 |
| 控制比赛 | 提高控球和中场稳定性、减少无序转换 | 直接机会与比赛速度下降 |
| 均衡应对 | 接近球队和阵型本身的基准表现 | 没有明确专项优势 |
| 快速反击 | 降低控球和射门总量，提高转换机会占比与质量 | 长时间承压、阵地进攻能力下降 |
| 低位防守 | 压缩禁区、降低对方机会质量 | 自身控球、进攻和扳平能力明显下降 |

建议初始边界：

- 策略带来的控球目标修正限制在约 `±4～12` 个百分点。
- 单项攻防强度修正原则上不超过 `±6%`。
- 低位防守不能同时获得高防守、高反击质量和完整进攻能力。
- 快速反击应表现为“更少但更危险的转换”，不能简单增加射门总数。
- 主动压迫第一版只改变当场节奏、机会和风险，不额外引入跨场持续疲劳债务。
- 策略应影响权威 MatchStats 和事件来源，而不是赛后随机补控球、射门或角球数字。

## 8. 自动决策规则

### 8.1 决策输入

- 教练风格、评分、风险倾向、抗压和赛事适性。
- 双方整体实力及攻/中/守结构差异。
- 主场、客场或中立场；世界杯东道主仍按中立场规则处理，只保留已有东道主氛围加成。
- 联赛、普通杯赛、决赛、两回合次回合和当前总比分。
- 实际可用阵容、伤停和各大位置人数。
- 球队士气、势头与疲劳。
- 小幅且可重放的独立确定性扰动。

### 8.2 决策原则

- 首选阵型默认保持不变，比赛上下文主要改变策略，而不是频繁随机换阵。
- 强队主场更倾向主动压迫或控制，不能保证必选。
- 弱队客场面对明显实力差时更倾向低位防守或快速反击。
- 中立场不应用主客场策略倾向。
- 杯赛决赛和两回合次回合应读取真实淘汰条件；领先方更保守、必须追分方提高风险。
- 高疲劳球队降低主动压迫权重，严重后场伤停降低高位投入权重。
- `riskBias` 调整策略概率，不把决策变成固定 if/else。
- 建议保留约 `10%～15%` 的权重扰动，使同类教练不会得到完全相同部署，但同一场比赛必须确定性重放。

示例而非硬规则：

```text
防守型教练 + 客场弱队 + 实力差 12
低位防守 50% / 快速反击 30% / 均衡 15% / 其他 5%

控球型教练 + 主场强队 + 体能良好
控制比赛 50% / 主动压迫 30% / 均衡 15% / 其他 5%
```

## 9. 软克制与数值预算

### 9.1 不使用硬阵型矩阵

阵型和策略先转换为少量内部维度，再比较双方：

- `width`：边路宽度与拉扯能力。
- `centralControl`：中路人数和控球支点。
- `compactness`：防线与中场间距、禁区保护。
- `lineHeight`：整体站位高度及身后空间。
- `transitionThreat`：夺回球权后的快速推进威胁。
- `directThreat`：双前锋、传中和直接进攻威胁。

可解释关系示例：

- 宽度高的一方能够拉扯高度收缩的防线，但高位投入会给反击留下空间。
- 4-2-3-1 通常能在中路限制 4-4-2，但未必能击穿 5-4-1 的禁区密度。
- 主动压迫可能破坏控球推进，也可能被快速反击利用身后空间。
- 5-4-1 能降低中路机会质量，却要接受更低控球和更少自身机会。

### 9.2 强制上限

- 单独的对位克制建议限制在约 `±3%`。
- 阵型、策略、克制和教练执行合并后的单项效果原则上限制在约 `±6%`。
- 教练原有攻防 buff 和赛事 buff 必须进入同一预算，禁止重复叠加到两位数百分比。
- 每场最多向玩家展示一项主要优势和一项主要代价，避免把内部参数全部倾倒到 UI。
- 战术可以改变胜率，但不能覆盖明显的球队和球员实力差。

- [ ] 将策略影响接入控球、预期进球、射门量、机会质量、比赛波动和事件倾向。
- [ ] 将软克制转化为有上限的模型修正和结构化解释。
- [ ] 重构当前 `underdog_response`，由弱队策略承担主要真实性表达；不得继续叠加无条件进攻补偿。
- [ ] 统一教练评分、攻防 buff、风险倾向和赛事适性的职责及总效果上限。
- [ ] 中立场、世界杯东道主、德比和主场加成继续保持各自独立语义。
- [ ] 保证无教练、缺阵型、极端属性和非法输入均有稳定回退。

### 11.2 事件与统计一致性

- [ ] 控球、射门、射正、角球、定位球和关键事件的变化必须来自同一比赛模型。
- [ ] 战术只调整事件发生倾向，不得修改已经确定的比分后再补装饰性统计。
- [ ] 反击策略提高 `counter` 来源占比，不能把普通进攻仅改名为反击。
- [ ] 宽度和直接打法可以影响传中、角球或边路演出占比，但不凭空改变比分。
- [ ] 红牌后的阵型压缩、控球和机会倾向与实际少一人状态一致。
- [ ] 战术重构不得破坏球员进球、助攻、扑救、防守事件和在场失球的权威归属。

## 14. 可维护性要求

- [ ] 阵型定义、位置数量、战术维度和文案标签分别集中在明确模块，避免循环依赖。
- [ ] 比赛引擎只处理数值和结构化原因，不生成 React 文案。
- [ ] Canvas 只解释战术快照，不重新判断强弱、教练风格或比赛策略。
- [ ] UI 文案由枚举格式化器和原因代码生成，禁止页面内散落 switch 副本。

- [ ] 添加开发期分布审计，但普通生产构建不暴露新的 `window` 调试桥。

## 18. 最终验收定义

方案 B 完成时，玩家应当能够在不打开直播的情况下回答：

1. 这位教练通常使用什么阵型、偏好怎样比赛？
2. 双方今天采用什么部署，为什么？
3. 该部署给比赛带来了什么优势和代价？
4. 弱队爆冷是来自合理的防守与反击倾向，还是单纯随机加成？
5. 教练更替后，球队在数值、比赛画像和故事表达上发生了什么变化？

打开直播后，画面中的阵线、宽度、转换和播报必须与上述答案一致。只有做到“数值真实、解释一致、画面可见、长期可追溯”，这套系统才算完成。
